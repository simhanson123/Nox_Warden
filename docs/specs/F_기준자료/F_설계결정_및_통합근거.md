# 최종 설계 결정 및 통합 근거

문서 상태: 최종 설계 기준 / 작성일: 2026-10-30 / 판: 1.0

이 문서는 두 설계안, 상호 비교평가, 개발 계약과 검증 기록에서 무엇을 채택하고 무엇을 바꿨는지 설명한다. 제품의 규범적 동작은 함께 제공하는 최종 아키텍처 설계서를 따른다. 여기서의 ‘채택’은 설계 결정의 확정이며, 구현·성능·실장비 검증을 마쳤다는 뜻이 아니다.

## 1. 판단 원칙

출발점은 모델 간 우열이 아니라 같은 요청을 끝까지 안전하게 처리할 수 있는가다. 자연어 요청, 승인, 정책 배포, 패킷 처리, 만료, 장애 복구가 서로 다른 의미를 사용하면 각 부분이 그럴듯해도 전체 제품은 안전하지 않다. 따라서 다음 순서로 판단했다.

1. 실제 패킷과 권한의 의미가 명확한가.
2. 승인받은 내용과 실제 실행이 같은 대상·범위·기한에 결합되는가.
3. 중단·응답 유실·재시작·시계 변화 때도 그 의미가 유지되는가.
4. 무엇을 검증했고 무엇을 검증하지 못했는지 구분되는가.
5. 한 명의 유지관리자가 시작하여 공개 기여를 받을 수 있는 범위인가.

분량이 많다고 구현이 완성된 것은 아니며, 범위가 작다고 원래의 제품 목표를 모두 충족한 것도 아니다. 작은 집행 핵심과 넓은 확장 구조를 함께 보존하되, 확장 기능마다 실제로 쓰기를 허용하는 진입 조건을 둔다.

## 2. 자료의 버전과 증거 수준

### 2.1 비교평가서를 최신 원문보다 우선하지 않는다

과거 정밀 비교평가와 `tmp/GPT_review/GPT_implementation_test_receipt.json`이 검토한 Claude 원문의 SHA-256은 아래의 구판 값이다. 이번에 제공된 현재 원문은 다른 해시를 가진다. 따라서 과거 평가서의 행 번호와 결함 판정을 현재 원문에 그대로 옮기지 않았다.

| 자료 | SHA-256 | 취급 |
|---|---|---|
| 현재 Claude 설계 원문 | `f00e27207d4cad1590cfc17604545ebe97ab08c1a83535208774ca7b76400004` | 최신 설계 의도와 현재 계약의 기준 |
| 과거 평가가 대상으로 삼은 Claude 원문 | `4a51a19ffee21448f4170e19a27fbdaa438cac18130897a50b2988384a80c1d1` | 당시 판정의 범위를 식별하는 값 |
| 현재 GPT 설계 원문 | `662d83577d68cf84df096b5816f3a30c2bb22dbdf85067a935545f6768e00d05` | 실행 계약과 제품 범위를 대조하는 기준 |

문서 내 C는 `Claude_Rampart_오픈소스_AI통제형_방화벽_최종아키텍처_설계서.md`, G는 `GPT_오픈소스_방화벽_최종_아키텍처_설계서.md`를 가리킨다. 이 표기는 출처 식별용이며, 결과물의 명칭이나 제품 이름이 아니다.

### 2.2 기존 시험 기록을 과장하거나 지우지 않는다

기존 검증 JSON은 스키마·예제·문서 검사와 추출한 Rust 인터페이스의 컴파일·일부 테스트를 기록한다. 과거 구현 검토 영수증에는 7개 Rust 테스트 통과가 기록되어 있고, 동시에 제품 빌드·패킷·벤더 시험은 아니라는 범위가 명시되어 있다.

현재 C 부록 K의 12번 항목은 Linux 5.15 및 nftables 1.1.3 환경에서 연결 표시 타임아웃, 절대 시각 만료, 충분한 잔여 시간의 세 가지 netns 시험을 수행했다고 보고한다. 두 만료 사례는 8초 뒤 차단, 유지 사례는 20초 지속으로 적혀 있다. 이는 원문에 보고된 제한된 시험 결과로 인정한다. 제공된 `tmp`의 관련 Markdown·JSON·셸·로그 파일에서는 이 최신 시험의 실행 스크립트와 원로그를 확인하지 못했다. 그러므로 독립 재현 완료나 전체 stateful 방화벽 검증 완료로 확대하지 않는다. 같은 부록의 bridge 시험은 커널 모듈 부재로 수행하지 못했다고 명시되어 있다.

최종 패키지의 검증도 ‘문서·계약 검사’, ‘실행 가능한 참조 모델 검사’, ‘커널 패킷 시험’, ‘실장비 시험’을 각각 표시한다. 어느 하나의 통과를 다른 단계의 통과로 바꾸지 않는다.

## 4. 최신 원문에 대한 재판정

| 이전 쟁점 | 현재 원문의 상태 | 최종 판단 |
|---|---|---|
| established 선허용으로 임시 연결이 계속 살아남음 | C §15.2는 strict 이중 만료, 연결 표시 판정표, flowtable 금지를 추가했다 | 이전 결함이 그대로 남았다고 평가하지 않는다. 다만 주소 축소 후 정리 지연과 겹친 허용의 세션 의미를 추가로 정리한다 |

| deny 삭제가 무조건 Low | C §12.1·12.6은 Δ+로 변경 위험을 계산하고 허용 확대의 자동 병합을 금지한다 | 해결된 의도를 채택한다. 차단의 검토 시각과 자동 종료 시각은 별도 필드로 정리한다 |
| timeout 뒤 무조건 재시도 | C §14.5는 UNKNOWN, 영속 일지, 재조회, 대상 동결을 명시한다 | 보완을 인정한다. 대상 장비의 원자 fencing 여부는 추가로 구분한다 |

| DB 복구 후 과거 세대 재사용 | C §7.3·14.5는 장비·증적과 최대 epoch/seq를 비교한다 | 보완을 인정한다. 확인되지 않은 대상은 복구 상태로 유지하고 자동 쓰기 재개를 금지한다 |

## 5. 확정한 설계 결정

### D01. 정책 의미는 순서 없는 허용 합집합에서 차단 합집합을 뺀다

업무 흐름의 허용은 `Permit(t) = Union(유효 allow, t) - Union(유효 deny, t)`로 정의한다. 별도 보호되는 관리·네트워크 제어 baseline은 이 업무 규칙 집합과 구분한다. 요청자는 priority를 바꾸어 차단을 우회할 수 없다.

C의 first-match 모델은 기존 벤더 정책을 손실 없이 가져오는 데 유리하다. 그러나 신규 제품의 v1에는 사용자가 바꿀 수 있는 priority, 앞선 deny 목록, shadow 분석, 기존 세션의 rule ownership까지 함께 구현해야 하는 비용이 생긴다. G의 단순 모델을 선택하고, 기존 first-match 설정은 읽기·분석 전용으로 가져온다. 쓰기 대상으로 전환하려면 독립 의미 비교가 통과해야 한다.

검수: 입력 규칙의 순서를 바꿔도 허용 집합·판단·산출물 의미가 같아야 한다. 겹치는 allow가 있어도 deny는 우선한다.

### D02. 세션 권한은 현재 허용 집합으로 판정한다

한 흐름에 A와 B가 동시에 권한을 주면 A의 만료만으로 B의 유효 권한까지 사라지지 않는다. 마지막 유효 allow가 끝나거나 deny가 적용되면 이후 패킷은 차단한다. 회수 결과에는 다른 유효 권한이 남는지를 표시한다.

이 선택은 G의 ‘특정 policy/version에 연결을 귀속하고 자동 승계하지 않음’과 C의 ‘첫 일치 규칙 표시로 유지’ 양쪽을 수정한다. 하나의 연결이 어떤 허용 규칙을 우연히 먼저 만났는지에 따라 종료 시각이 바뀌는 문제를 없앤다. 업무별 연결을 반드시 구분해야 하는 경우에는 실제 워크로드 격리나 별도 네트워크 식별자가 필요하다.

conntrack mark는 현재 정책의 의미를 보존하는 캐시일 수 있다. mark 자체를 영구 승인으로 사용하지 않는다. 정책 변경은 활성 버전 및 캐시 유효성을 원자적으로 바꾸고, 후속 패킷은 현재 정책으로 재검사한다. 주소·포트·인터페이스 축소 후 conntrack 삭제가 완료되기 전까지 구 권한이 통과하는 구간을 허용하지 않는다. conntrack 삭제는 정확성의 전제보다 후속 정리 작업으로 둔다.

검수: A/B 중첩, A 회수, B 만료, deny 추가, 주소 축소, 규칙 재정렬, 에이전트 종료를 조합한 양방향 TCP·UDP 시험을 한다.

### D03. 상태 기반 방향과 패킷 방향을 혼동하지 않는다

업무 정책의 방향은 연결을 시작한 방향이다. 반환 패킷을 반대 방향의 신규 접근으로 다시 해석하지 않는다. 원래 방향의 주소·서비스 튜플, IP family, protocol, 신뢰되는 인터페이스/영역, conntrack direction을 함께 사용한다. NAT를 지원하지 않는 v1의 범위를 분명히 유지한다.

일반적인 `established,related accept`는 사용하지 않는다. 자동 conntrack helper를 끄고, 관련 ICMP 오류·PMTUD·필수 IPv6 제어 통신은 별도 명시적 프로필과 시험으로 다룬다. 예상하지 못한 비대칭 경로나 워크로드 식별 실패는 더 넓은 허용으로 바꾸지 않는다.

### D04. allow 만료와 deny 검토를 다른 계약으로 둔다

임시 allow의 `expires_at`은 집행 종료 시각이다. deny의 `review_at`은 사람이 재검토할 시각이며 자동 차단 해제 시각이 아니다. v1에서는 deny의 자동 만료·삭제를 지원하지 않는다. 제거 요청은 새 계획의 Δ+를 검증하고 승인받는다.

C의 `on_expiry: review/remove`는 차단 해제의 위험을 잘 드러냈다. G의 deny `expires_at` 의미 보정도 같은 위험을 인지했다. 최종본은 필드 자체에서 의미를 분리해 독립 SDK나 UI가 잘못 해석할 가능성을 줄인다. 자동 대응 차단의 종료는 후속 RFC에서 시작·종료를 함께 승인한 별도 수명주기로 정의한다.

### D05. 필수 검증의 UNKNOWN은 승인 점수로 덮지 않는다

검증 결과는 PASS, FAIL, UNKNOWN, NOT_APPLICABLE을 구분한다. 필수 검사가 UNKNOWN 또는 모델 밖이면 그 계획은 배포할 수 없다. 위험 등급 상승과 추가 승인으로 정확성 부재를 대체하지 않는다.

C §11.5의 BDD 예산 초과를 보증 공백 점수로 올리는 방식은 검증 범위를 넓힐 수 있다는 장점이 있지만, 불변식의 성립을 확인하지 못한 상태가 쓰기 허가로 바뀔 수 있다. 최종본은 지원 범위를 좁히거나 검증을 다시 수행해 PASS를 얻도록 한다. 비필수 참고 분석의 미실행은 별도 coverage로 공개할 수 있다.

### D06. 노출 위험과 중단 위험을 함께 승인한다

Δ+는 새로 열리는 흐름이고 Δ-는 닫히는 흐름이다. Δ+가 비었다고 업무 영향까지 작은 것은 아니다. deny-all, 중요 서비스 차단, 관리 경로 변경은 노출을 줄이면서 큰 장애를 만들 수 있다.

양쪽의 위험 점수는 설명과 우선순위에 사용한다. 정책 위반·검증 실패·관리 경로 보호·핵심 업무 중단 조건은 점수와 별도 강제 조건이다. 안전한 자동 회수는 만료된 allow의 정리 등 좁은 경로에서만 허용한다.

### D07. 하나의 계획은 하나의 집행 대상을 가진다

최소 실행 단위는 target 하나, 그 target의 승인된 baseline 하나, 후보 artifact 하나다. PlanContent의 해시는 스냅샷·정규화 IR·도구 버전·검증 결과·영향·기한과 결합한다. 승인과 실행 권한은 이 해시를 참조한다.

여러 대상의 작업은 별도 workflow가 대상별 계획과 상태를 모은다. 전체 성공은 필요한 모든 대상의 영수증으로 확인하며 일부 성공을 전체 ACTIVE로 표시하지 않는다. 여러 장비와 DB를 하나의 원자 트랜잭션이라고 부르지 않는다.

### D08. UNKNOWN 상태에서 재시도보다 관측을 먼저 한다

장비가 쓰기를 처리한 뒤 응답이 유실되면 실패로 단정하지 않는다. 먼저 영속 일지와 장비 재조회로 적용·미적용·부분 적용을 구분한다. 불확실한 동안 동일 쓰기를 다시 보내거나 관련 예산을 반납하지 않는다.

양쪽 최신 계약의 일지·단일 writer·재조회 원칙을 채택한다. 복구도 현재 시점의 유효 권한만 복원하며 이미 만료·철회된 allow를 되살리지 않는다. 복구 후 패킷 손실이나 외부 서비스의 부작용까지 취소된다고 주장하지 않는다.

### D09. lease와 실제 fencing을 구분한다

네이티브 집행기는 자신이 저장한 epoch/generation보다 오래된 명령을 실제 적용 경계에서 거부한다. DB lease만 보유했다는 사실로 충분하다고 보지 않는다.

C §14.5의 벤더 주석 `rp-gen` 선조회 후 쓰기는 유용한 충돌 탐지지만 compare-and-swap이 아니다. 구 작성자가 낮은 값을 읽은 뒤 멈췄다가 새 작성자의 적용 뒤 쓰면 이전 정책을 덮을 수 있다. 장비가 제공하는 잠금·조건부 변경·세션 fencing을 검증하지 못한 어댑터에는 네이티브와 같은 강한 동시성 보장을 붙이지 않는다. 해당 관리 범위에 direct API와 외부 관리 도구를 동시에 writer로 두지 않는다.

### D10. 관리 접근 확인은 실제 신규 연결로 한다

기존 agent 연결의 생존, 로컬 리스닝 포트, 설정의 lifeline 존재는 각각 유용하지만 원격 관리자의 신규 연결 성공과 같지 않다. production 관리 경로를 바꾸는 배포는 대표 관리 출발지의 새로운 연결 탐침을 요구한다. 탐침은 대상·계획·세대·일회 challenge에 결합한다.

C가 보강한 별도 탐침 키와 G의 신규 관리 연결 요구를 함께 보존한다. 로컬 watchdog은 적용 전에 시작한다. 확인이 없으면 유효한 안전 복구 상태로 돌아가며, 복구도 확인하지 못하면 대상 상태를 DEGRADED로 남긴다.

### D11. 시각·재부팅·재개를 같은 만료 계약에 포함한다

커널 상대 timeout과 신뢰 UTC에 따른 절대 기한은 서로 다른 고장을 막는다. 하나만으로 모든 환경의 정확한 기한을 보장하지 않는다. 신뢰 시각을 확인하지 못한 부팅에서는 임시 허용을 복원하지 않는다.

v1의 인증된 집행 프로필에서는 suspend/hibernate 및 live snapshot restore를 지원하지 않는다. 해당 기능을 추가하려면 재개 첫 패킷 이전의 격리, 시각·권한 epoch·만료 재검증을 실제 환경에서 입증해야 한다. ‘재개 후 사용자 공간이 언젠가 탐지’하는 방식으로 절대 만료를 보장하지 않는다.

### D12. AI 권한 경계는 프로세스·자격증명으로 강제한다

내부 통역 AI는 DraftIntent를 만들고, 외부 에이전트는 요청이나 제안을 낸다. 둘 다 장비 쓰기 자격증명과 승인 권한을 갖지 않는다. 독립 signer는 controller의 `approved=true` 같은 DB 값을 그대로 믿지 않고 승인 대상과 권한 근거를 검증한다.

C의 독립 signer, 공급자 프로세스 격리, Laya 식별과 작업별 평가 접근을 채택한다. G의 공급자와 에이전트 호스트 구분, 제한된 호출 표면도 유지한다. 특정 브랜드나 typed output·confidence를 보안 판정의 근거로 사용하지 않는다. 구독 CLI 연결은 도구 실행을 사전에 제한할 수 있는 검증된 경로에서만 사용한다. read-only나 사후 결과 폐기는 무도구 실행 보장이 아니다.

### D13. 봉투는 범위 상한이며 인증·위임·예산을 대신하지 않는다

즉시 허용의 조건은 승인된 봉투, 등록 주체, 현재 워크로드 결합, 위임 범위, 조직 가드레일, 잔여 예산의 교집합이다. 요청의 출발지는 인증 주체의 검증된 바인딩에서 정하며, 요청 본문으로 바꾸지 않는다.

v1은 등록된 루트 주체의 단일 위임 범위를 지원한다. 하위 에이전트의 동적 생성과 재위임은 후속 단계로 둔다. 확장 시 부모·조직 예산은 자식 수가 늘어도 증가하지 않으며 권한과 만료는 부모 범위 안으로만 줄어든다.

서명된 activation에는 principal, workload binding revision, 봉투/위임 digest, reservation, target, protocol, 절대 기한, 재생 방지 식별자가 결합된다. 독립 서명 및 집행 경계에서 다시 확인한다.

### D14. 동적 허용의 키와 소유권을 완결한다

C §19.5의 예시 JIT 집합은 `(src,dst,port)`라 protocol이 없다. 동일 주소·포트의 TCP와 UDP가 봉투에 함께 있으면 한쪽 activation이 다른 쪽 정적 규칙에도 사용될 수 있다. 최종 계약의 흐름 키에는 적어도 IP family, protocol, source, destination, service와 집행 범위를 포함한다.

같은 흐름에 여러 grant가 있으면 단일 집합 원소 삭제로 소유권을 구현하지 않는다. 승인 원장은 grant별 권한과 기한을 보존하고 집행기는 현재 유효 grant들의 합집합을 투영한다. 한 grant를 철회해도 다른 grant를 지우지 않으며, 마지막 권한이 끝나면 원소와 후속 패킷 허용이 끝난다. 만료를 갱신할 때 과거 메시지의 재전송으로 기한이 늘어나지 않는다.

### D15. 네트워크 식별자가 없으면 에이전트별 패킷 격리를 주장하지 않는다

MCP 토큰 검증은 요청자 확인이다. 같은 IP·network namespace·NAT 출발지를 공유하는 두 프로세스의 실제 패킷을 IP 방화벽이 구별하게 해 주지는 않는다.

C의 바인딩, L2 격리와 anti-spoof 요구를 보존한다. 격리된 VM/namespace, 신뢰되는 인터페이스·주소 할당, 재할당 방지 조건이 없으면 제품은 공유 네트워크 주체 단위의 허용만 보장한다. 주소 재사용은 남은 grant와 conntrack을 고려하여 지연하거나 격리한다.

### D16. 운영 일꾼은 제안하고 오래된 작업 결과는 거부한다

드리프트 조사, 정리 후보, 탐지 규칙 초안, 감사 요약 등 C의 운영 직무를 유지한다. 결과는 정해진 schema에 맞는 데이터이며 자동 승인이나 직접 배포 명령이 아니다.

작업 claim에는 `claim_generation`과 불투명 token을 발급한다. heartbeat, update, complete는 현재 소유자·generation·유효 임대를 비교해 원자적으로 갱신한다. 오래된 worker의 완료와 파생 제안은 거부한다. 재시도 가능한 후속 요청은 작업 ID와 허용된 action revision에 결합한 멱등 키를 쓴다.

### D17. MCP는 공통 애플리케이션 서비스를 운반한다

도구 schema는 외부 사용자 정의 URI를 해석해야만 동작하는 형태로 배포하지 않는다. wire schema는 필요한 정의를 내부에 묶는다. 성공·업무 거절·시스템 오류·비동기 상태의 닫힌 결과 형식을 제공하고, 페이지 조회 입력·출력 및 operation별 결과 형식을 함께 정의한다.

짧은 요청 안에 끝나지 않은 작업은 operation ID와 상태 조회 경로를 반환한다. timeout을 미적용으로 해석하지 않으며, 호출 취소와 이미 발급된 접근권한 회수를 구분한다. 사람이 이해하는 화면과 에이전트용 인터페이스는 같은 권한 검사와 상태 전이를 사용한다.

### D18. 작은 실행 코어와 명확한 프로세스 경계를 유지한다

Rust 도메인 모듈, AI 프로세스, signer, 권한 있는 집행기를 분리한다. 그 밖의 접수·조회·작업 조정·관측 기능을 처음부터 모두 분산 서비스로 배포하지 않는다. SQLite는 단일 controller 프로필에 한정하고, 다중 controller는 PostgreSQL 및 별도 동시성 검수 뒤 제공한다.

자체 Git 포지, 자체 OAuth 인가 서버, DNS 리졸버, DHCP 서버, Wasm 플러그인 호스트를 첫 핵심 기능의 전제로 두지 않는다. 기존 도구와 최소 계약을 사용하고, 직접 구현해야 할 제품상 이유와 유지보수 인력이 생길 때 분리된 RFC로 추가한다. 단일 박스라는 제품 가치는 유지하되 같은 호스트의 여러 Unix 사용자 분리가 root 침해까지 막는다는 주장은 하지 않는다.

### D19. 문서 계약과 출시 지원 상태를 분리한다

JSON Schema의 통과는 올바른 권한을 뜻하지 않는다. 타입 범위, 참조 무결성, 인증, 기한, 서명, baseline, 현재 대상 상태를 추가로 검사한다. 문서용 생략 부호를 실제 digest 값으로 허용하지 않는다. 예제는 실제 길이의 합성 digest를 사용하며, 런타임 검증과 참조 모델 검사를 별도로 보고한다.

‘지원 예정’, ‘읽기/렌더’, ‘계약 시험’, ‘실제 쓰기 검증’을 구분한다. nftables의 커널 트랜잭션 원자성을 모든 벤더나 여러 대상의 원자성으로 확대하지 않는다. 잘못된 기능을 더 넓은 allow로 근사하는 fallback은 금지한다.

### D20. GitHub 공개는 재사용 권리와 실제 품질 약속을 분리한다

자체 작성 코드·문서·예제의 공개 라이선스는 최종 공개 지침에서 정한 Apache-2.0 정책을 일관되게 따른다. 외부 코드·규칙·모델·이미지의 라이선스는 별도로 보존한다. 코드의 서명·취약점 접수·지원 범위·증거 있는 릴리스 노트는 라이선스 선택과 별개 운영 책임이다.

기존 C의 문서 CC BY 4.0과 G의 다중 산출물은 그대로 혼합하지 않는다. 실제 기여물의 권리 상태를 확인하고, 최종 새 저작물의 표시를 정리한다. 라이선스가 보안 사고나 모든 법적 책임을 없앤다고 설명하지 않는다. 구체적인 보호 범위와 공개 전 권리 점검은 별도 라이선스 지침을 따른다.

## 6. 확장 목표와 쓰기 허용 관문

| 확장 목표 | 보존하는 제품 가치 | 쓰기를 허용하기 전의 필수 조건 |
|---|---|---|
| NAT | 가정·사무실 게이트웨이와 포트 포워딩 | original/transformed tuple, route/filter 순서, 기존 NAT 세션, rollback, lifeline 보호를 별도 의미 모델과 패킷 시험으로 검증 |
| FQDN egress | 이름 기반 개발 서비스 접근 | DNS snapshot과 갱신 권한, TTL 상한, rebinding, 공유 IP, 부정 조건의 건전한 상·하한 분석; hostname 강제와 IP 허용을 구분 |
| Bridge | 주소 변경 없는 삽입 | L2·ARP·IPv6·브리지 conntrack, 부팅 전 격리, 루프·관리 경로 및 실제 모듈 적합성 시험 |
| XDP | 대량 공격의 조기 drop | DROP/PASS만 제공하고 PASS 뒤 nft 검사 유지; fragment·IPv6·응답 방향·보호 흐름·map 갱신·자원 상한 시험 |
| Suricata inline IPS | 허용 흐름의 콘텐츠 검사 | 정책 허용 후 별도 hook, 양방향 검사, 무리스너·queue 포화·재시작을 구분한 fail-open/closed, offload 우회 금지 |
| HA | 게이트웨이 장애 시 복구 시간 단축 | 정책 version·동적 권한·만료·conntrack mark 동기화, split-brain fencing, 시각, standby의 실제 경로 검수 |
| 벤더 쓰기 | 기존 투자와 공존 | 버전별 capability, 독립 importer, 장비 잠금·CAS, 부분 적용·미확정·세션 만료·보상 복구 실장비 시험 |
| 하위 에이전트 | 대규모 AI 작업 조직 | 위임 체인 진위, 감쇠 권한, 합산 예산, 동시 예약, root 정지 전파, 재생·재할당 시험 |
| 자동 대응 | 탐지에서 제한된 차단까지 단축 | 인증된 탐지 근거, 위조 출발지 배제, 보호 목록, 시작·종료 범위 사전 승인, 오탐 복구 시험 |
| Wasm 플러그인 | 커뮤니티 어댑터 | 허용된 IO 중개, 비밀 비노출, 자원·호스트·경로 제한, 계획 밖 쓰기 차단, 독립 읽기 검증 |

Suricata 공식 문서는 nftables 방화벽 판정 뒤의 별도 IPS 체인을 설명하며 `bypass`는 queue listener가 없는 경우의 동작을 바꾼다. queue 포화까지 같은 실패로 단순화하지 않는다. [Suricata NFQUEUE 구성](https://docs.suricata.io/en/suricata-8.0.1/ips/setting-up-ipsinline-for-linux.html)

nftables flowtable은 일반 forwarding 경로를 우회하므로, 만료·재검증·IPS와 함께 쓰려면 그 빠른 경로 자체를 시험해야 한다. [nftables 공식 매뉴얼](https://www.netfilter.org/projects/nftables/manpage.html)

## 7. 채택하지 않은 주장

- Rust나 typed output만으로 논리 오류·메모리 누수·환각이 사라진다는 주장.
- BDD, 서명된 증적, schema 통과를 전체 네트워크의 형식 증명으로 부르는 표현.
- 날짜나 모델 버전이 적혀 있다는 이유만으로 외부 SDK·장비 기능이 검증됐다는 주장.
- source IP가 같아도 MCP principal이 다르면 패킷을 자동 구별할 수 있다는 주장.
- 라이선스만 선택하면 상용 재사용·상표 침해·보안 사고·제3자 권리 문제까지 해결된다는 주장.
- 문서나 비교점수의 우수성이 출시 준비 완료를 뜻한다는 주장.

## 8. 최종 검수에 연결할 반례

| 반례 | 실패하면 안 되는 동작 |
|---|---|
| allow A가 만료되지만 B는 유효함 | 규칙 순서 때문에 B 권한까지 조기 종료하거나 A를 영구 연장하지 않는다 |
| allow 객체의 주소 하나가 제거됨 | conntrack 정리 전 구 mark로 해당 주소의 패킷을 계속 허용하지 않는다 |
| TCP/53 grant만 있고 봉투에는 UDP/53도 있음 | UDP/53이 함께 활성화되지 않는다 |
| 같은 흐름에 grant 두 개가 있고 하나만 회수 | 다른 유효 grant의 권한과 증적을 삭제하지 않는다 |
| 필수 Twin 계산이 예산을 초과함 | 높은 위험 점수나 사람 승인만으로 PASS로 바꾸지 않는다 |
| target이 적용했으나 응답이 유실됨 | 동일 쓰기 재전송이나 예산 선반납을 하지 않는다 |
| 이전 writer가 멈췄다가 뒤늦게 재개 | 최신 target generation을 낮은 값으로 덮어쓰지 않는다 |
| 기존 관리 TCP는 살아 있지만 신규 연결은 차단됨 | 배포를 정상 확정하지 않는다 |
| 작업 A의 임대 만료 뒤 B가 점유 | 오래된 A의 완료·후속 제안을 받지 않는다 |
| 과거 snapshot을 만료 뒤 복원 | 이전 허용을 첫 패킷부터 다시 사용할 수 있게 하지 않는다 |
| 기존 설정에 순서 예외가 있음 | 순서를 삭제하고 의미가 달라진 union 정책을 동등하다고 표시하지 않는다 |
| public FQDN deny를 넓게 근사함 | 실제 허용 상한을 줄여 계산하고 안전하다고 판정하지 않는다 |

이 반례들은 구현 수용 기준이다. 이번 최종 설계 산출물에서 해당 장비·커널 시험까지 수행했다는 의미로 읽지 않는다.
