# 등록·내부 통신·권위 부트스트랩 명세

**F-2.0 · 공용 REST와 분리된 service 통신 계약**

## 1. 공통 봉투와 전송

내부 메시지는 F_내부통신_스키마.json의 closed tagged object를 사용한다. 공용 사용자 API가 이 메시지를 전달받았다고 특권 작업을 수행하지 않는다. HTTPS mTLS의 별도 agent listener(`/internal/v1/messages`)와 로컬 Unix socket/ACL된 Windows named pipe/macOS XPC를 사용한다. 로컬 IPC에서도 peer OS identity를 확인하고 payload의 actor 문자열을 신뢰하지 않는다. 원격 agent는 outbound 연결을 기본으로 하여 target에 공개 관리 포트를 요구하지 않는다.

`schema_version`, `message_id`, `correlation_id`, `target_id`, `authority_epoch`, `target_generation`, `sent_at`, `deadline`, `kind`, `body`를 가진다. UUID와 UTC whole-second를 사용한다. authority_epoch와 target_generation은 기존 core 계약과 같은 10진수 문자열이며 런타임에서 uint64 범위를 검사한다. sender identity·org·project는 mTLS 인증서와 현재 registry에서 얻는다. 한 메시지 최대 1MiB, 최대 TTL 300초, long poll 최대 25초, request timeout 30초, 최대 동시 in-flight 4개/target, 초당 10개/target을 시작값으로 한다. 초과 429, malformed 400, auth 401/403, stale epoch/generation 409, expired 410, unsupported 422다. 오류 body는 F_02 Problem 계약과 같은 code/correlation 의미를 사용하되 비밀을 노출하지 않는다.

각 reply는 request message ID에 결합한다. 새 권한 쓰기는 이미 존재하는 signed Grant/PolicyChangeGrant와 정확히 같은 target/epoch/generation에 한정한다. message의 deadline을 늘려 grant의 not_after나 allow expiry를 연장하지 못한다. transport success는 policy active가 아니다.

## 2. Target 등록

관리자는 `doctor`로 OS/CPU와 target의 새 transport public key fingerprint를 확인한다. enrollment 권위는 기존 owner 권한 또는 로컬 bootstrap의 신뢰 root로만 생성한다. token은 CSPRNG 256bit 이상, 10분 단일사용, 저장소에는 hash만 보관하며 expected target ID·org/project·key fingerprint·OS·승인자·만료와 결합한다. target은 private key를 로컬 OS 보호 저장소에 생성하고 외부로 내보내지 않는다. transport certificate는 TLS용 key이고 policy 서명 Ed25519 key와 분리한다.

초기 `/internal/v1/enroll`은 정상 TLS 및 명시적으로 전달한 controller trust fingerprint로 서버를 검증한다. 인증되지 않은 최초 연결에 TOFU로 서버를 조용히 신뢰하지 않는다. request는 enrollment request schema의 token, CSR, expected fingerprint, nonce, platform, agent version이다. CSR 자체 서명/허용 algorithm/key strength/CSR public key fingerprint를 독립 검사하고 token에 결합된 값과 비교한다. client가 CSR에 임의로 쓴 SAN/역할은 무시하고 인증서 SAN은 서버가 target identity로 만든다.

DB는 token unused→reserved를 CAS하고 CSR hash를 고정한 뒤 CA 작업을 수행한다. 같은 token·CSR retry는 같은 등록 결과를 반환하고 다른 CSR은 거절한다. certificate 저장과 token consumed/target registered/audit/outbox는 한 transaction에서 완료한다. CA 응답 유실은 같은 issuance job 조회로 복구하고 다른 target을 중복 생성하지 않는다. 발급 후 runtime 권한은 새 capability와 승인된 baseline을 확인할 때까지 observe-only다.

response는 target ID, certificate chain, trust bundle hash, assigned authority epoch, renewal 시각을 포함한다. private key·enrollment token을 reply/log에 넣지 않는다. 인증서 최대 수명 24시간, 8시간마다 갱신 시도, 정상 겹침 최대 1시간을 초기값으로 한다. 갱신은 현재 mTLS key 및 registry 권한으로 요청하고 revoked target에는 거절한다. 인증 실패 시 기존 데이터 평면 만료는 유지하되 신규 grant 수신/적용을 중지한다. 인증서가 유효하다는 사실만으로 철회된 target이 다시 권한을 얻지 못한다.

## 3. 메시지 종류와 정확한 책임

| kind | body 필드 | 처리 |
|---|---|---|
| `poll` | `last_message_id` nullable, `capability_hash`, `observed_state_hash` nullable | target이 대기 명령을 조회. heartbeat는 readback 인증을 대신하지 않음 |
| `dispatch` | `operation_id`, `grant_hash`, `artifact_hash`, `candidate_hash`, `baseline_hash`, `capability_hash` | trusted object store에서 exact bytes를 취득하고 모두 검증한 뒤 apply |
| `observe` | `operation_id` nullable, `expected_state_hash` nullable | 실제 native 상태를 읽으라는 요청, 쓰기 권한 아님 |
| `observation` | `operation_id` nullable, `readback_report_hash`, `observed_state_hash` nullable, `status` | Native ReadbackReport 증거 참조. UNKNOWN을 null 대신 성공으로 처리 금지 |
| `confirm` | `operation_id`, `grant_hash`, `state_hash`, `probe_report_hash` | exact operation/epoch/generation/hash 및 probe 확인 후 durable confirm CAS |
| `receipt` | `operation_id`, `receipt_hash`, `installation_manifest_hash` nullable | 기존 Core Receipt/PolicyChangeReceipt와 installation evidence의 exact bytes 참조 |
| `reconcile` | `operation_id`, `grant_hash`, `expected_state_hash` | 상태 확인·승인된 복구만. 임의 rollback rule 제공 금지 |
| `revocation` | `revocation_manifest_hash` | 서명된 authority tombstone을 검증·durable 저장·적용; 수신만으로 flow 회수 완료 아님 |
| `ack` | `acknowledged_message_id`, `status`, `evidence_hash` nullable | accepted/duplicate/rejected 구별. accepted는 active가 아님 |

수신자가 취득할 수 있는 hash 객체는 인증된 제어/권위 저장소에 현재 tenant·target·operation과 연결된 것뿐이다. payload에 fetch URL·파일 경로·shell command가 없다. object reader는 요청 범위와 최대 16MiB/256KiB chunk 제한, digest, media type, closed schema, DSSE signature/trust를 확인한다. Artifact에 포함된 외부 executable 참조를 실행하지 않는다.

`message_id`의 exact body hash를 target journal에 보존한다. 같은 ID+같은 hash는 기존 결과, 같은 ID+다른 hash는 충돌이다. restart 후에도 epoch/generation 최고값과 replay ledger가 남아야 한다. dispatch 응답 유실 시 poll/observe로 확인하고 새 generation을 발급하여 중복 허용하지 않는다. journal을 잃은 target은 fresh enrollment/authority epoch 전이 전 쓰기 불가다.

## 4. 독립 signer 인터페이스

controller→signer의 `sign-plan` 입력은 plan hash, approval-set hash, quota reservation ID, authority epoch, target ID, generation이다. 원본 객체는 signer가 권위 저장소에서 읽는다. controller가 전달한 PASS, quota 합산, approval=true를 신뢰하지 않는다. F_03의 예약→서명→재검증→dispatch 2단계를 따른다. 출력은 grant hash와 exact signed bytes이며 signer job ID로 멱등 처리한다. Grant hash는 JSON 재직렬화 이전의 정규 봉투 bytes와 일치해야 한다.

policy signer는 임의 bytes를 서명해주는 범용 endpoint가 아니다. 허용된 payloadType/권한/현재 root/project 한도/승인·time·baseline을 독립 검증한다. 키 회전은 old/new key가 허용되는 명시된 구간을 가진 signed trust manifest로 수행한다. keyid를 권한으로 보지 않고 해당 key의 목적과 tenant를 확인한다. 긴급 키 철회는 새로운 grant 발급 중지와 target tombstone 전달·reconcile을 함께 수행한다.

## 5. 초기 권위 manifest와 순환 없는 승인

`AuthorityBootstrapManifest`는 manifest ID, schema version, org/project/target, old epoch nullable, new epoch, 생성/만료시각, trust-root hash, management-baseline hash, envelope hash 목록, delegation hash 목록, capabilities hash, reason을 포함한다. 모든 hash는 이미 준비된 immutable object를 가리킨다. manifest 자체에 그 manifest를 승인한 최종 ApprovalSet hash를 넣어 순환 hash를 만들지 않는다.

승인 proof는 별도 객체로 `subject_type=authority_bootstrap`, `subject_hash=manifest hash`에 결합한다. WebAuthn challenge·origin/RP ID·현재 owner 역할·독립성·만료를 F_02 방식으로 확인한다. 권위 signer는 manifest와 검증된 proof를 묶은 `BootstrapAuthorization`을 DSSE로 서명한다. payloadType은 `application/vnd.f.authority-bootstrap.v1+json`이다. trust root는 기존 신뢰 경로 또는 로컬 OOB ceremony에서 확인하며 자기 서명 public key만으로 신규 root를 원격 승인하지 않는다.

import 시 old epoch/current head, new epoch 단조성, manifest/proof/signature, scope·주소·서비스·time·quota, baseline·capability를 검증한다. atomic import 후 target이 새 epoch를 durable 저장하고 baseline+probe를 확인한다. 중간 실패는 pending/unknown으로 남기고 manifest 재시도는 같은 job으로 수렴한다. root 초기 등록과 root 확대는 모두 감사되며 기존 키를 가진 controller가 이를 혼자 우회할 수 없다.

## 6. 시험과 구현 상태

IPC01: 다른 tenant certificate로 dispatch 거절. IPC02: token 재사용/다른 CSR/만료/틀린 fingerprint 거절. IPC03: CA응답 유실 후 같은 issuance로 복구. IPC04: same ID/different bytes 거절. IPC05: old epoch·generation·stale capability 거절. IPC06: grant hash와 artifact bytes 불일치 거절. IPC07: forged confirm이 다른 operation watchdog을 취소하지 못함. IPC08: stale authority manifest·자기 승인 root·순환 hash 거절. IPC09: 인증서 만료/철회 시 신규 확대 중지, 이미 적용된 allow 만료 유지. IPC10: 관측 UNKNOWN이 active로 변환되지 않음.

이 계약은 M02/M03/M05/M08에서 구현한다. 현재 제공한 schema 검증은 wire 형태에 대한 검사이며 TLS handshake, PKI, signing, OS peer credential, replay journal 또는 runtime 권한 검증의 통과가 아니다.
