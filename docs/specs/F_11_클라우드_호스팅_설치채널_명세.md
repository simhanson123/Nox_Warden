# 클라우드·호스팅·설치 채널 명세

판본: F-2.0 · 2026-10-30 · 상태: 구현 및 검수 계약

목표는 AWS, Google Cloud, Azure, Hostinger, IBM Cloud, Oracle Cloud, Alibaba Cloud의 관리 권한을 가진 서버와 직접 운영하는 WordPress 서버에 같은 제품을 설치하는 것이다. Linux·Windows Server·macOS의 실제 native 집행 범위는 `F_09_멀티플랫폼_설치_집행_명세.md`를 따른다. 이 문서는 제품 binary·공개 저장소·npm package·클라우드 VM을 이미 만들거나 배포한 결과가 아니다.

## 1. 설치 가능성의 판단 기준

클라우드 브랜드보다 실행 환경의 권한·OS·집행 경계가 먼저다. 다음 조건을 모두 확인한다.

1. OS와 CPU가 release의 실제 검수 matrix에 포함된다.
2. 사용자가 OS 서비스와 해당 native 집행기를 설치할 root/관리자 권한을 적법하게 가진다.
3. 서명·driver·Network Extension 승인 등 OS별 전제 조건을 충족한다.
4. VM 재시작 뒤에도 저널·신원·generation·만료 정보를 보존할 영속 디스크가 있다.
5. 관리 경로와 provider console 등 복구 경로를 확보하고 초기 정책을 관측·검증할 수 있다.
6. provider 보안그룹·라우팅·OS 방화벽의 소유권과 서로 다른 의미를 구별한다.

SSH/WP-CLI를 사용할 수 있다는 사실만으로 root·kernel·서비스 설치 권한이 있다고 판단하지 않는다. 기능이 없으면 `UNSUPPORTED_PROFILE` 또는 필요한 권한 부족을 정확히 반환한다. 권한을 얻으려고 shared hosting의 격리를 우회하지 않는다.

## 2. 제공자별 배포 계획

아래 표의 VM 경로는 설치 대상 후보이며 제품 검수 완료 표가 아니다. provider의 최신 image·region·OS 지원과 F_09의 실제 통과 조합이 겹치는 범위만 release에서 지원한다. 모든 provider가 모든 OS를 제공한다고 주장하지 않는다.

| 제공자 | 설치 대상·접근 | 제품 설치와 provider 경계 | 반드시 남길 검수 증거 |
|---|---|---|---|
| AWS | EC2 Linux/Windows에서 허용된 SSH·Systems Manager 또는 Windows 관리 경로. macOS는 실제 EC2 Mac 전용 하드웨어 제공 범위 | guest에 native package 설치. Security Group/NACL/route는 별도 제어면. 기본 import/read-only이며 기존 SG를 자동 수정하지 않음 | instance/image/OS/backend 버전, console 복구, SG와 host rules 양쪽 관측, 기존 연결 만료·재부팅 |
| Google Cloud | Compute Engine의 지원 Linux/Windows VM, SSH/OS Login·IAP 또는 Windows 관리 경로 | guest 집행과 VPC firewall/hierarchical policy를 구분. 서비스 계정의 cloud 권한은 읽기 목적에 필요한 최소 범위 | VM image·OS권한, VPC/host 차단 지점 구별, 관리 경로 재접속·reboot |
| Microsoft Azure | Azure VM Linux/Windows, SSH/RDP·Bastion 등 허용된 관리 경로 | guest 집행과 NSG·Azure Firewall·route를 구분. managed identity가 host 관리자 권한을 자동 뜻하지 않음 | VM/image/NSG 연결·OS backend·새 관리 연결·복구 결과 |
| Hostinger | root 접근 가능한 VPS와 F_09에 맞는 Linux image | hPanel/VPS firewall과 guest nftables 별도. Web/Cloud/managed WordPress 상품을 VPS와 동일하게 보지 않음 | VPS 상품·배포판·root/service 권한, 기존 panel firewall 소유권·재부팅 |
| IBM Cloud | VPC Virtual Server Instance의 지원 OS와 SSH/RDP 등 허용된 관리 경로 | VPC security group/ACL과 guest 집행 분리. instance/cloud IAM 권한과 guest 계정 구별 | VSI/image/security group·OS backend·console/OOB·만료/복구 |
| Oracle Cloud | OCI Compute의 지원 Linux/Windows instance, SSH/Remote Desktop·console | NSG/security list·route와 guest 방화벽 분리. Oracle Linux image의 기존 방화벽을 임의로 끄지 않음 | image/shape/CPU·guest권한·VCN/host 영향 구분·reboot/read-back |
| Alibaba Cloud | ECS의 지원 Linux/Windows, Workbench/Session Manager/SSH/RDP·VNC 복구 | Security Group과 guest 집행 분리. RAM 권한만으로 승인 없는 제품 정책 쓰기 권한을 부여하지 않음 | instance/image·SG·guest filter·관리 경로·동일 세션 만료·VNC 복구 |

위의 접근·서비스 구분 근거는 각 제공자의 공식 문서다. [AWS SG와 host firewall](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-security-groups.html), [AWS EC2 Mac](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-mac-instances.html), [Google Linux VM 연결](https://docs.cloud.google.com/compute/docs/connect/standard-ssh), [Azure VM 연결](https://learn.microsoft.com/en-us/azure/virtual-machines/linux-vm-connect), [Hostinger 서버 권한](https://www.hostinger.com/support/which-server-capabilities-are-supported-at-hostinger/), [Hostinger VPS 접속](https://www.hostinger.com/support/5577900-how-to-log-in-to-your-vps-at-hostinger/), [IBM Linux VSI 연결](https://cloud.ibm.com/docs/vpc?interface=ui&topic=vpc-vsi_is_connecting_linux), [OCI instance 관리](https://docs.oracle.com/en-us/iaas/Content/Compute/Tasks/instances.htm), [Alibaba ECS 연결](https://www.alibabacloud.com/help/en/ecs/user-guide/connect-to-instance), [Alibaba OS 보안](https://www.alibabacloud.com/help/en/ecs/user-guide/operating-system-security/).

macOS는 F_09의 native Network Extension·서명·사용자/MDM 승인 조건을 그대로 만족해야 한다. EC2 Mac에 OS가 있다고 해당 extension이 자동 승인되는 것은 아니다. 다른 provider에 macOS 이미지를 임의로 올릴 수 있다고 가정하지 않는다. 서버리스 함수·관리형 DB·Cloud Run/App Service 같은 관리형 runtime·권한 없는 container는 native host firewall 설치 대상이 아니다. 해당 서비스는 별도 제어 가능 자원으로 import하거나 외부에 허용된 controller의 UI/API client만 사용할 수 있다.

## 3. WordPress 호스팅

| 형태 | 가능 범위 | 제공하지 않는 기능 |
|---|---|---|
| root 권한을 가진 VPS/전용 서버에 WordPress 직접 설치 | 같은 OS에 native 방화벽 설치, 웹 서버·DB·관리 접근을 좁은 정책으로 관리 | PHP 취약점·SQL injection·WordPress 사용자 권한을 L3/L4로 해결했다고 주장하지 않음 |
| shared/managed WordPress, 서버 root 없음 | 제공자 firewall/WAF 설정 활용, 공개 문서·UI client 사용, 제공자가 허용한 읽기 연동 | WordPress plugin 하나로 kernel firewall/driver/Network Extension을 설치하거나 전체 서버 보호 |
| WordPress.com의 제한된 SSH/WP-CLI | 제공자가 허용한 사이트 파일·WordPress 관리 | SSH 기능을 OS 관리자 권한으로 확대 해석 |
| WordPress를 container로 직접 운영 | root host에 설치한 집행기가 실제 namespace·bridge·route 소유권을 확인한 지원 profile | container에 설치한 CLI가 host와 다른 tenant까지 보호한다는 주장 |

WordPress.com 공식 SSH 안내는 사이트 파일·설정과 WP-CLI 접근을 설명한다. 이를 일반 서버 관리자 권한의 근거로 사용하지 않는다. [WordPress.com SSH](https://wordpress.com/support/ssh/)

초기 WordPress 배포의 baseline은 기존 관리 경로, 실제 웹 listener, 실제 DB endpoint, DNS/time/update dependency를 관측해 승인한다. DB를 무조건 인터넷에 열거나 WordPress 관리자 로그인을 방화벽 관리 인증으로 재사용하지 않는다. 외부 CDN의 전체 주소가 아니라 운영자가 승인한 실제 route/원본 접근 계약을 사용하고, 주소 변경에 대한 FQDN 자동 확장은 검수된 별도 profile이 없으면 지원하지 않는다. backup·plugin 업데이트·메일·health check를 포함해 양성/음성 시험을 수행한다.

WordPress plugin을 추가하는 경우 native host 제품과 별도 package로 둔다. plugin의 기본 기능은 사용자가 등록한 controller의 제한된 상태 조회와 관리 UI 연결이며, WordPress 관리자 자격으로 host root·제품 approver 권한을 얻지 않는다. WordPress credential을 controller에 전달하거나 plugin update hook으로 native installer를 자동 실행하지 않는다. 허용 endpoint·인증 scope·SSRF 방어와 private network 접근 정책을 별도로 검수한다.

자체 제작 native core의 Apache-2.0을 유지하면서, 새 WordPress plugin은 GPL 호환 배포 단위로 별도 관리한다. 구현 시 plugin 자체에 `GPL-2.0-or-later`를 적용하고 포함한 코드·JS·이미지의 호환성을 검사하는 것을 기본 경로로 삼는다. Apache core binary/소스를 plugin zip에 섞어 전체를 Apache 또는 GPL 하나로 표시하지 않는다. HTTP 연동이라는 이유만으로 모든 결합·재배포 쟁점이 자동 해소됐다고 단정하지 않고 실제 포함물·결합 방식을 감사한다. WordPress.org directory는 GPL 호환 라이선스, 사람이 읽는 source/build 접근, 추적 동의 등을 요구하므로 공식 지침 검수를 별도 출시 gate로 둔다. [WordPress 라이선스 설명](https://wordpress.org/about/license/), [Plugin Directory 지침](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/)

## 4. host 방화벽과 cloud 방화벽의 책임 분리

native host agent가 관리하는 것은 해당 OS의 승인된 enforcement scope다. VPC 전체·다른 VM·provider 관리 서비스로 효과를 확대해 표시하지 않는다. cloud SG가 허용해도 host는 차단할 수 있고, host allow만으로 cloud SG/route의 차단을 우회할 수 없다. 경로 화면은 각 layer의 관측 시각과 권한 범위를 함께 표시한다.

초기 cloud adapter의 기능은 `inventory.read`, `rules.import`, `topology.read`, `diff.report`다. API 자격증명은 읽기 범위로 제한하고 product 배포 signer/enforcer와 분리한다. AWS SG의 허용 규칙·stateful 동작을 프로젝트의 deny 우선·strict expiry와 같은 것으로 변환하지 않는다. 다른 cloud rule의 priority·implicit rule·statefulness도 원래 의미를 보존한다. 분석 coverage가 없으면 UNKNOWN이다.

cloud 쓰기를 추가하려면 provider별 capability/schema, 의미 보존, 동시 writer 통제, eventual consistency 관측, API quota, 실패 중간 상태, rollback, 여러 resource의 부분 성공, credential 분리와 실제 account 시험을 완료해야 한다. provider API의 성공 응답을 실제 전체 경로 ACTIVE로 판단하지 않는다. 이 진입 조건 전에는 cloud rule 쓰기를 API/UI/CLI 모두 거절한다.

VM을 routed gateway로 사용할 때는 별도 검수 profile을 선택한다. IP forwarding, provider별 source/destination 검사, route next hop, 대칭 반환, multi-NIC, MTU, 관리 경로가 실제로 충족되어야 한다. installer가 기본 route·VPC route·IP forwarding을 자동으로 변경하지 않는다. 단일 VM의 전원/region 장애에 대한 HA나 우회를 제공한다고 주장하지 않는다.

## 5. 모든 설치 채널의 공통 artifact 계약

설치 채널이 달라도 같은 release manifest와 서명된 native artifact를 사용한다. manifest는 `release_version`, `source_commit`, `schema_version`, `os`, `arch`, `package_kind`, `artifact_sha256`, `artifact_size`, `signing_identity`, `provenance_ref`, `sbom_ref`, `license_manifest_ref`, `min_os`, `backend`, `cli_entrypoint`, `migration_version`를 가진다. 모든 참조는 검증된 release 저장소의 고정 파일이며 임의 사용자 URL을 실행 대상으로 받지 않는다.

binary/package 이름과 다운로드 origin은 실제 공개 이름·저장소·서명 주체를 정한 release manifest가 공급한다. 현재 문서에 존재하지 않는 `curl` URL·npm package 이름·가짜 GitHub release를 써서 바로 설치 가능한 명령으로 가장하지 않는다. `cli_entrypoint`는 해당 release의 실제 executable 이름이며 이하 표는 그 executable 아래의 구현할 subcommand 계약이다.

지원 installer는 Linux deb/rpm·서명 archive, Windows signed MSI/CLI zip, macOS signed/notarized app/pkg·CLI archive다. Windows driver와 macOS extension은 CLI zip만 풀어 완료된 것으로 처리하지 않는다. OS별 신뢰·권한·설치 상태는 F_09에서 검증한다. checksum만으로 발행자를 인증했다고 주장하지 않고 고정한 신뢰 root/서명 주체도 검증한다.

| 채널 | 사용자 경험 | 구현 제한 |
|---|---|---|
| native package/CLI | 기본 권장. 다운로드·검증·OS 설치·진단·observe-only | Node/Python/Docker/LLM·클라우드 계정이 runtime 필수 아님 |
| package manager | 검증된 native artifact를 참조하는 유통 경로 | apt/rpm/winget/Homebrew 등록 여부는 별도 release 상태 |
| npm wrapper | Node 환경 사용자의 선택적 client/bootstrap launcher | firewall 자체를 JavaScript process로 바꾸지 않음; 자동 root postinstall 없음 |
| AI Skill | 인간이 검토할 진단·설치계획·표준 CLI 호출을 돕는 지침 | Skill 설치가 OS driver 설치·조직 승인·sudo 권한을 부여하지 않음 |
| cloud-init / image bake | 승인한 image에 고정 artifact를 배치하는 자동화 | host enforcement 활성화를 무검증 자동화하지 않음 |
| Terraform | 사용자가 고른 VM/network resource의 생성계획·출력 연결 | 제품 정책 승인과 cloud resource 변경승인은 별도 |

## 6. native CLI 설치 흐름

각 subcommand는 `--json`을 지원하고 stdout에는 안정된 machine result, stderr에는 비밀 없는 진단을 출력한다. JSON은 canonical 영어 state/code·UTC·확인된 artifact/hash·단계·지원 여부를 포함한다. 사람용 출력은 F_05 locale 정책을 따른다. `--help`와 조회는 elevated 권한 없이 실행한다.

| Subcommand | 입력·결과 | 부작용·권한 |
|---|---|---|
| `version` | binary/release/commit/schema/backend 정보 | 읽기만 |
| `doctor` | OS/CPU/권한/기존 관리자/clock/디스크/복구 경로 점검 | 읽기만, secret 출력 금지 |
| `install plan` | 서명된 manifest와 로컬 배포 profile→설치할 파일·서비스·권한·재부팅·hash | 변경 없음 |
| `install apply` | 위의 고정 install plan hash→OS package 설치 영수증 | 실제 OS 관리자 승인, 검사한 같은 artifact만 실행 |
| `status` | 서비스와 target capability·observe-only/enforced/pending 승인 | 읽기만, installer 완료와 보호 활성 구별 |
| `enroll` | 단일 사용 enrollment token과 target fingerprint/CSR | token 비밀 입력, 서버/target 검증 후 등록 |
| `bootstrap plan` | 관리 경로·root authority/baseline manifest→검토 hash | 변경 없음, F_02 bootstrap 절차 |
| `bootstrap apply` | 정확한 승인 증거·manifest→initial baseline 작업 | 독립 signer·OS enforcer, read-back/probe/confirm 필요 |
| `upgrade plan` / `upgrade apply` | 고정 새 release와 migration 영향→동일 검증 설치 | 기존 정책·만료·최고 generation 보존 |
| `uninstall plan` / `uninstall apply` | 제품 소유 파일·서비스·필터·데이터 유지 여부 | 타 방화벽은 제거하지 않음. 정책 제거의 노출 영향 명시 |

실제 설치 순서는 artifact/signature 검증 → doctor → install plan → OS 권한에 따른 apply → 서비스·ACL·DB migration → loopback bootstrap → target enrollment → capability probe → 관리/OOB 복구 확인 → observe-only → 승인한 baseline 적용 → 새 관리 연결·양성/음성 probe와 read-back → enforced다. 단계 실패 시 그 단계와 관측을 남기며 '설치 성공=보호 완료'로 표시하지 않는다.

update 다운로드 중 실패는 기존 버전·정책을 유지한다. 교체는 checksum·signature·schema compatibility 확인 후 수행하며 migration backup과 복구 절차를 남긴다. downgrade는 schema/권한 rollback을 자동 허용하지 않는다. offline 설치도 같은 artifact/manifest/trust bundle을 매체로 전달해 검증한다. 개발자 서버 접속·telemetry·후원 확인은 설치 조건이 아니다.

## 7. npm wrapper의 범위

배포 전에 실제 scope/package 소유권·registry provenance·버전·license·의존성을 확인한다. 공개 package가 없으면 문서의 설치 버튼은 native 다운로드 안내만 제공하며 임의 npm 이름을 활성 링크로 만들지 않는다.

wrapper는 선택적 편의 도구다. npm `install`/`postinstall`에서 firewall rule 변경·서비스 설치·sudo/UAC 호출·secret 탐색·외부 script 실행을 하지 않는다. 사용자가 명시적으로 launcher의 `install plan`/`install apply`를 실행했을 때만 native installer 흐름을 보여준다. elevated 실행은 OS installer가 수행하고 npm 프로세스 전체를 상시 관리자 서비스로 실행하지 않는다.

wrapper는 release manifest를 선택한 고정 버전으로 확인하고, OS/arch에 맞는 native artifact를 내려받아 digest·서명·발행자·길이·압축 해제 경로를 검증한다. archive path traversal·symlink escape를 거절하고 검증 전에 실행하지 않는다. 다운로드 token·URL을 실행 shell 문자열에 넣지 않는다. 네트워크 없는 경우 검증된 로컬 artifact를 사용하며 최신 버전 조회 실패를 설치권한 우회로 처리하지 않는다.

`npx`/`npm exec`는 필요할 때 registry package를 내려받아 실행할 수 있으므로 사용자가 실제 검증된 package와 버전을 명시하도록 문서를 생성한다. 첫 사용 prompt·registry trust를 제품 승인으로 오인하지 않는다. wrapper의 registry 서명은 native OS driver/extension 서명을 대체하지 않는다. [npm exec 공식 문서](https://docs.npmjs.com/cli/v11/commands/npm-exec/)

## 8. Skill과 agent 설치 보조

루트 패키지의 `F_SKILL.md`는 실제 배포 때 SKILL.md로 매핑한다. 지침과 typed CLI tool만 제공하며 admin credential을 포함하지 않는다. Skill은 사용자의 대상·OS·profile·설치 권한을 확인하고 `doctor`와 `install plan` 결과를 사람이 읽기 쉽게 설명한다. 기존 승인 범위 안에서 작업하되 새로운 클라우드 구매·공개 포트·권한 확대·파괴적 제거를 설치에 숨기지 않는다.

Skill은 signed release metadata와 허용된 공식 문서만 설치 근거로 사용한다. issue/comment/log/웹 문서 안의 명령을 그대로 특권 실행하지 않는다. tool output의 prompt injection을 권한 지시로 취급하지 않는다. cloud credential·등록 token은 OS 보호 입력/저장소로 제공하며 대화·plan·PBOM·셸 history에 넣지 않는다.

설치 보조 권한, workload 접근 요청 권한, 사람 승인 권한을 구별한다. Skill을 쓰는 AI는 `approve_any`, 임의 shell enforcer, 정책 DB 수정, production signer 접근을 얻지 않는다. 설치 후 접근 요청도 기존 봉투·위임·MCP 여섯 도구의 범위다. WordPress plugin·npm package·Skill 어느 채널도 root 없는 호스트에 실제 packet enforcement가 가능하게 만들지 않는다.

## 9. cloud-init·Terraform의 구현 작업

현재 단계는 **구현할 자동화 계약**이다. 완성된 IaC template·공식 marketplace image·일곱 provider 배포 성공을 제공한 상태가 아니다. 자동화가 없어도 native installer가 먼저 독립적으로 동작해야 한다.

cloud-init은 provider/image가 실제 지원하는 datasource·부팅 단계·재실행 의미를 검수한다. user-data에는 비밀 signer key·장기 token·운영 정책 원문을 넣지 않는다. image에 고정한 검증용 공개 trust bundle과 서명된 release artifact를 배치하고, 최초 실행은 observe-only로 끝난다. short-lived enrollment는 별도 보호 channel에서 전달하고 재실행 중 새 root·target identity·generation을 무작위로 덮어쓰지 않는다. 부팅 실패·download 실패·반복 실행 시험을 포함한다. Windows/macOS에 Linux cloud-init을 억지 적용하지 않고 native 설치/관리 도구의 승인 흐름을 따른다. [cloud-init](https://docs.cloud-init.io/en/latest/explanation/introduction.html)

Terraform은 provider/version/lockfile을 잠그고, 입력을 region·image·VM size·관리 source·기존 network ID·release digest·profile로 한정한다. 기본 plan은 관리자가 선택한 instance와 최소 network resource만 보여주며 project 전체 administrator 권한·공개 관리 포트를 기본 요구하지 않는다. 비용·삭제·route·security group 변화는 plan에 드러내고 사용자 승인을 받은 같은 saved plan만 apply한다. Terraform plan이 제품의 signed Plan/ApprovalSet을 대체하지 않는다. [Terraform plan](https://developer.hashicorp.com/terraform/cli/commands/plan)

state/plan 파일은 비밀을 포함할 수 있으므로 공개 저장소에 넣지 않고 암호화·접근 제어·잠금·backup을 적용한다. credentials는 짧은 수명/최소 권한을 우선하고 제품 runtime에 이관하지 않는다. `destroy`는 별도 명시 작업이며 운영 정책 증적·backup·다른 서비스 자원을 지우는 기본 정리 스크립트를 만들지 않는다.

## 10. 경량성과 최대한 안정적인 기본값

기본 runtime은 Rust 서비스, Lite SQLite, 해당 OS의 native executor, 정적 React assets다. Node·Python·Docker·Kubernetes·LLM·Redis·Kafka·대형 SIEM을 필수로 두지 않는다. cloud adapter·모델 worker·IDS·telemetry는 별도 선택 process이며 꺼진 기능은 CPU·메모리·외부 연결을 소비하지 않아야 한다.

F_01/F_07의 RSS·API·만료·장기 실행 목표를 cloud image에서도 다시 측정한다. `경량`은 단일 파일이라는 표현이 아니라 idle/peak RSS, CPU, disk, kernel state, 부팅 시간, packet throughput, 파일 descriptor, 7일 memory plateau로 평가한다. 도메인 안정성을 위해 signer/executor/watchdog의 권한 경계를 합치지 않는다. 성능 수치는 실제 측정 전 목표로 표시한다.

모든 설치는 backoff·deadline·resource bound·재시작 복구를 가진다. 제어면이 느려지거나 cloud API가 실패해도 기존 native 집행과 만료가 유지되어야 한다. provider metadata·internet·GitHub·npm·telemetry가 중단되어도 설치된 방화벽이 라이선스 확인을 기다리며 멈추지 않는다.
