# 데이터베이스·동시성·복구 구현 명세

상태: 구현 계약 / 실제 DB 경합·장애 시험 전. 날짜: 2026-10-30. 이 문서는 API·도메인 명세, 확장 JSON Schema, 집행·복구 명세를 함께 적용한다. 예시 테이블명은 `fw_*` 모듈의 내부 SQL 이름이며 제품명과 무관하다.

## 1. 저장소의 책임

Lite/Lab은 한 controller의 로컬 SQLite WAL을 사용한다. SQLite 파일을 SMB/NFS/iCloud/OneDrive 동기화 폴더에 놓거나 여러 controller가 공유하지 않는다. Linux, Windows Server, macOS 모두 동일한 logical repository 계약을 구현하되 OS 파일 잠금·권한·fsync 의미를 시험한다. Team은 PostgreSQL과 트랜잭션 행 잠금/RLS를 사용한다. Kafka/NATS를 기본 의존성으로 추가하지 않는다.

Git은 검토된 의도, controller DB는 요청/작업/desired revision, authority 원장은 승인·위임·예산, target 로컬 저널은 실제 집행 전후, evidence store는 불변 bytes를 보존한다. 어느 하나의 ACTIVE 문자열이나 commit만으로 실제 집행을 판정하지 않는다. Controller DB commit과 원격 target 적용은 분산 트랜잭션이 아니며 outbox, idempotency, fencing, signed receipt로 수렴시킨다.

Lite 연결마다 `foreign_keys=ON`, `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=5000`을 설정하고 확인한다. 논리 쓰기 트랜잭션은 `BEGIN IMMEDIATE`; read는 짧은 snapshot transaction이다. checkpoint 정책은 WAL 크기64MiB 또는 60초를 시작값으로 하고 DB backup/read를 굶기지 않도록 측정한다. 전원 장애 내구성을 보장하지 않는 저장장치·filesystem 설정은 지원 조합에서 제외한다. Team의 기본 isolation은 READ COMMITTED와 아래 명시 잠금이며 migration/복구에는 별도 maintenance mode를 사용한다.

## 2. 공통 logical 타입과 제약

아래 표는 dialect별 실제 migration이 반드시 구현해야 하는 normalized logical DDL이다. `PK`, `UK`, `FK`, `CHECK`, append-only와 트랜잭션 경계는 선택 사항이 아니다. 보안 객체를 한 JSON blob에 넣고 필요한 관계 검사를 생략하는 구현은 이 명세를 충족하지 않는다. canonical bytes는 증거 정본이고 normalized columns는 조회·잠금·제약을 위한 projection이다. insert 시 양쪽 일치 검증, 읽기 검증은 중요한 승인/집행 경로에서 반복한다.

| logical type | PostgreSQL | SQLite | 검증 |
|---|---|---|---|
| UUID | uuid | TEXT | lowercase canonical UUID; HTTP와 내부 import 모두 검사 |
| HASH | BYTEA(실제 CHECK octet_length=32) | BLOB CHECK length=32 | wire의 sha256:hex를 lossless 변환 |
| UTC_SECONDS | BIGINT | INTEGER | Unix 정수초, 유효 civil-time 범위; wire UTC 정수초 |
| U64 | NUMERIC(20,0), CHECK 0≤n≤18446744073709551615 | BLOB(8) big-endian unsigned | wire decimal→checked u64→8bytes; 정렬/비교는 unsigned lexicographic |
| REV | INTEGER CHECK 1..2147483647 | INTEGER 동등 CHECK | 증가 시 overflow 거절, wrap 금지 |
| JSON_BYTES | BYTEA | BLOB | UTF-8 canonical bytes; duplicates/NaN/unknown fields 거절 후 저장 |
| TOKEN_HASH | BYTEA length32 | BLOB length32 | token 원문 보관 금지, constant-time 비교 |

SQLite에서 U64를 REAL 또는 signed INTEGER로 우회하지 않는다. schema가 허용한 20자리 숫자는 의미 검증에서 u64 상한을 확인한다. DB adapter의 u64 encode/decode와 정렬 테스트는 0, 2^63−1, 2^63, 2^64−1 경계가 필수다. epoch/generation/claim_generation/sequence는 decrement·재사용·wrap 금지이며 고갈 시 신규 쓰기를 중지하고 명시 재등록한다.

tenant 소유 테이블에는 `org_id NOT NULL, project_id NOT NULL`가 있다. PK는 `(org_id,project_id,id)` 또는 표에 나온 복합키다. FK도 동일 tenant columns를 포함한다. UUID가 전역 유일하다는 가정으로 FK에서 tenant를 생략하지 않는다. global trust root 등 소수 전역 테이블은 별도 schema/repository와 관리자 connection에만 둔다. 소프트 삭제가 FK를 끊거나 감사 연결을 제거해서는 안 된다.

## 3. 관계형 테이블 계약

표에서 `T`는 `(org_id,project_id)`이고 모든 명시하지 않은 scalar는 NOT NULL이다. `?`만 nullable이다. `created_at`, `revision`, `content_hash`, `canonical_bytes`는 도메인 객체에 있는 경우 반드시 저장한다. UUID 관계의 실제 SQL명은 `_id`로 끝낸다. duration/count는 음수 불가, enum은 CHECK 또는 참조테이블로 제한한다.

정책 snapshot과 registry snapshot은 개념이 다르다. desired state hash를 registry snapshot hash로 대체하지 않는다. 계획 단계에서 request와 prospective lease ID를 먼저 할당하며 lease row는 pending이고 grant나 활성 권한이 아니다. 불변 registry/authority basis→request/prospective lease→candidate/plan→approval→grant 순서로 관계를 만든다. candidate association의 authority_basis_hash는 PolicyAuthorityBasis(approval requirements와 envelope/delegation 근거)의 hash다. 최종 ApprovalSet→plan 연결은 grant/PBOM에 별도로 보존한다. 따라서 최종 ApprovalSet hash를 candidate에 넣고 plan이 다시 그 candidate를 hash하는 순환이 없다. pending lease의 plan_id는 후보 계산 중 nullable로 두고 plan 저장 transaction에서 확정하며, plan이 확정되기 전 quota/grant/실행 대상이 될 수 없다는 CHECK와 서비스 검사를 적용한다.

## 4. 트랜잭션 경계

모든 transaction은 필요한 row의 부분집합만 잠그되 다음 전역 순서를 따른다: authority/project head → registry heads(ID순) → quota buckets(project→root ID순) → target/writer → request/plan(ID순) → approval challenge/set → lease/operation → work item/claim → inbox/outbox → audit head. 선행 row를 놓친 채 후행 row를 이미 잡았다면 transaction을 재시작한다. 여러 target을 잠그는 변경은 core-v1에서 허용하지 않는다. DB deadlock 감지 시 전체 transaction을 같은 idempotency key로 제한 재시도하며 성공한 외부 IO를 반복하지 않는다.

### T1 — 요청 접수

인증/입력 byte 제한→shape/의미 기본검사→tenant 결정 후 transaction 시작. idempotency row를 조회/생성하고 body hash 비교. 요청 및 immutable revision, validation operation, audit event, outbox event, 초기 응답을 한 번에 commit한다. outbox enqueue 실패 시 request만 남는 부분 성공은 없다. commit 뒤 response 전 연결이 끊겨도 동일 key가 동일 operation을 돌려준다.

### T2 — registry revision

project security head와 해당 asset/service head를 잠그고 ETag를 비교한다. immutable revision과 normalized children을 insert, current pointer를 CAS 갱신, security revision 증가, audit/outbox commit. 관련 plan을 즉시 stale 표시하거나 dispatch 때 revision fingerprint 비교로 막되, 관련 변경을 지나친 broad cache가 누락해서는 안 된다. 이미 적용된 권한을 수정하는 경우에는 별도 revocation/reconcile operation이 필요하다.

### T3 — 계획 생성

read snapshot에서 request/registry/authority/capability/baseline hashes를 고정하고 transaction 밖에서 결정적 compile/analysis를 수행한다. 완성 artifact bytes를 durable store에 쓰고 hash를 확인한 후 짧은 transaction에서 snapshot이 아직 current인지 재검사한다. 달라졌으면 STALE 결과를 기록하고 새 계획을 만든다. 일치하면 immutable plan/gates/evidence refs/operation succeeded/audit를 commit한다. 임시 orphan artifact는 보존시간 뒤 GC할 수 있지만 DB가 참조하는 객체를 먼저 지우지 않는다.

### T4 — 사람 승인

authority head→plan→challenge row 순서로 잠근다. proof 검증의 비싼 계산은 가능한 transaction 밖에서 하되 commit 때 challenge unused/expiry, exact plan hash, 현재 역할/credential/requirements를 재확인한다. challenge consume, HumanApproval, quorum 충족 시 immutable ApprovalSet, audit를 원자 commit한다. 동일 principal 다중 credential은 다수 사람으로 세지 않는다. 두 reviewer가 동시에 마지막 승인을 할 때 ApprovalSet content hash/plan membership unique로 중복 set을 막고 같은 충족 결과로 수렴한다.

### T5 — grant 발급과 전달

1. 고정 lock order로 project authority, quota buckets(project→root UUID순), target, plan을 잠근다. 현재 승인·binding·envelope·delegation·baseline·capability·epoch를 확인한다. 모든 limit에 prospective 사용량을 더해 검사한다. plan.target_generation은 계획 시 current generation+1로 제안된 값이다. 발급 직전 여전히 그 값과 일치하는 경우에만 generation을 증가시키고 intent, quota/dispatch reservation, signer job을 생성해 commit한다. 두 계획이 같은 다음 generation을 제안했다면 하나만 발급되고 나머지는 STALE이다. 실패로 생긴 generation 공백은 되돌리지 않는다. 아직 target으로 보낼 outbox는 만들지 않는다.
2. signer가 immutable inputs와 authority proof를 독립 검증하고 exact grant를 서명한다. RPC 응답은 grant_id/plan_hash/payload_hash에 결합된다. signer 장애는 예약 상태로 재시도하며 generation을 되돌리지 않는다.
3. 짧은 transaction에서 동일 intent/reservation이 current이고 authority/baseline/approval/capability가 바뀌지 않았는지 다시 확인한다. 성공하면 signed grant 저장, 첫 lease 발급 quota event 기록, dispatch outbox와 audit commit. 실패하면 그 서명을 폐기하고 reservation을 적절히 해제한다. target 전달이 없었다는 증거가 있을 때만 active/dispatch slots를 반환한다.
4. sender는 commit된 outbox만 읽어 grant를 전송한다. target은 epoch/generation과 grant replay ledger로 검증한다. response loss는 UNKNOWN 후보이며 동일 grant를 조회/재전송한다. 새 generation을 발급해 중복 확대하지 않는다.

signing과 delivery 사이의 철회 race는 DB 재검사만으로 완전히 사라지지 않는다. target은 받은 최신 authority epoch/tombstone을 적용하고, grant validity 상한300초 및 revocation delivery/reconcile 절차를 따른다. 전체 시스템이 이미 전달된 offline grant를 즉시 원격 취소할 수 있다고 주장하지 않는다. 권한 확대를 중지하고 기존 만료 상한을 유지하는 범위, 최대 철회 지연과 OS watchdog 조건은 집행 명세의 필수 시험 항목이다.

### T6 — 영수증 수신

mTLS identity와 receipt signature/chain, exact grant/plan/target/epoch/generation을 검증한다. inbox message ID와 payload hash를 삽입하고, 중복은 기존 결과 반환. target/operation row를 잠가 허용 state transition만 적용한다. active receipt이면 observed semantic state, confirm, management probe, 시각 상한 근거가 필수다. receipt/audit/operation/lease 상태·dispatch reservation 해제를 한 transaction에 commit한다. 과거 receipt는 증거로 보존하지만 현재 generation의 상태를 덮지 않는다.

### T7 — 반납/철회/만료

idempotency + authority/lease/target head를 잠근다. revocation/tombstone을 먼저 기록하고 새 grant를 차단한다. 제한적 reconcile operation/outbox/audit를 commit한다. API202는 원장 기록/작업접수다. target 적용 확인 전 network-revoked로 표시하지 않는다. 자연 만료는 kernel/executor의 expiry가 집행 정본이며 controller scheduler 장애가 기한을 연장할 수 없다. quota active slot 해제는 verified result 또는 안전하게 판별된 expiry 증거와 연결한다. 불명확한 lease는 unknown으로 유지한다.

### T8 — worker claim/complete

claim은 eligible work row를 잠그고 state/available_at/deadline/attempt/expected_generation을 검사한다. generation+1, attempt+1, 15분 이하 lease, token digest, audit를 commit한다. heartbeat는 같은 generation/token/worker일 때 deadline 이하로만 연장한다. complete는 현재 미만료 claim을 잠가 result hash를 비교하고 result, draft candidate, completion receipt, outbox, audit를 원자 commit한다. timeout 재점유와 complete가 경합하면 먼저 잠금을 얻어 조건을 충족한 하나만 성공한다. 이전 generation은 결과를 저장할 수 없다.

## 5. quota의 정확한 산식

quota는 root와 project를 모두 적용한다. project 상한은 root 분할로 우회할 수 없고 root 상한은 request/worker/workflow 분할로 우회할 수 없다. 계산 기준 시각 `as_of`는 해당 transaction에서 한 번 읽은 신뢰 UTC다. rolling window는 정확히 `(as_of−86400s, as_of]`이며 경계 중복/누락을 fixture로 시험한다.

| 항목 | 비용 단위와 계산 |
|---|---|
| active leases | active/scheduled-for-imminent-dispatch/pending/unknown으로 예약된 고유 lease ID 수. 한 lease의 256 policies를 256개로 세지 않음 |
| new leases/day | window 안 최초 grant가 commit된 고유 lease ID 수 + 아직 commit 안 된 유효 예약의 신규 lease 수 |
| unique destinations/day | window event들과 유효 예약의 destination asset ID 합집합 cardinality. 다른 root/project bucket은 각각 계산 |
| cumulative lease seconds/day | 최초 승인 발급 시 request.lease_seconds를 lease당 한 번 합산 + 유효 예약 비용. 정책 수로 중복하지 않음 |
| concurrent deployments | 아직 결과가 확정되지 않은 dispatch reservation 수. 같은 grant retry는 추가 슬롯 없음 |

기존 allow를 일반 policy_change로 축소/제거할 때 신규 lease 비용은 0이고 dispatch slot만 소비한다. allow 확대/기간 연장은 이 경로에서 거절하므로 비용 회피가 없다. 신규 접근 lease의 모든 policy는 동일 요청 lease window 안에 있어야 한다. 각 policy가 더 짧더라도 요청된 승인 기간 비용을 줄여 쪼개기 우회를 허용하지 않는다. 반납·조기 종료·배포 실패는 이미 기록된 24시간 신규 발급/승인기간 비용을 환불하지 않는다. active/dispatch 슬롯과 rolling 비용을 혼동하지 않는다.

예약에는 각 bucket의 projected count와 destination membership을 명시 저장한다. signer가 보는 BudgetReservation은 정확히 이 transaction의 값과 window를 반영한다. SQL SUM/COUNT(DISTINCT) 결과와 ledger에 근거 없는 client supplied projected 숫자는 받지 않는다. 발급 전 취소는 미발급 예약을 해제할 수 있다. 예약 TTL이 지났다는 이유만으로 UNKNOWN이거나 이미 전송 가능한 signed grant의 슬롯을 반환하지 않는다. sweeper는 inbox/outbox/grant/target journal reconciliation으로 no-dispatch 또는 안전한 종료를 확인한 뒤 해제한다.

PostgreSQL은 모든 관련 quota_buckets를 정렬된 순서로 `SELECT ... FOR UPDATE`하고 동일 transaction에서 live reservations+window ledger를 계산/삽입한다. SQLite는 BEGIN IMMEDIATE가 controller 내 쓰기를 직렬화한다. cache는 읽기 추정치에만 쓰며 권한 판정은 DB source를 재검사한다. 시간당 materialized aggregate를 쓰더라도 정확한 window 경계와 distinct membership을 보정해야 하며 잘못된 count를 security_revision/hash로 감지하면 신규 발급을 중지한다.

## 6. outbox, 중복, fencing

outbox worker는 PostgreSQL `FOR UPDATE SKIP LOCKED` 또는 SQLite 짧은 write transaction으로 batch≤50개를 claim한다. claim generation과 expiry를 저장하고 transaction을 끝낸 뒤 IO한다. delivery는 at-least-once다. exactly-once 네트워크 실행을 주장하지 않는다. 수신자 inbox와 grant/request idempotency가 논리 중복을 제거한다. payload hash 불일치는 재시도가 아닌 충돌이다.

모든 재시도는 bounded exponential backoff+jitter, 최대 대기60초, job deadline을 따른다. authority/grant 만료 후 dispatch를 재시도하지 않는다. worker inference attempt는3회, target dispatch는 유효 grant의 같은 ID 재시도만 허용한다. 후속 재계획은 새 ID와 근거를 가진다. dead-letter에는 원인, 마지막 state, 복구 action을 남기되 자동으로 승인 권한을 높이지 않는다.

controller writer lease는 가용성 조정용이다. target이 실제로 fence해야 한다. target local journal은 accepted max epoch/generation, exact grant hash, intent/applied/confirmed/rolled-back 상태를 durable하게 기록한다. 동일 generation의 다른 hash 거절, 낮은 generation 거절, 동일 grant replay는 과거 결과를 반환한다. VM/DB snapshot 복원으로 controller counter가 낮아지면 target과 독립 checkpoint의 최댓값을 확인하고 authority 재등록 전 quarantine한다. `MAX(DB, target, independent checkpoint)`보다 낮은 값으로 자동 초기화하지 않는다.

## 7. tenant isolation과 권한 저장

모든 repository method는 인증 middleware가 만든 `TenantContext`를 필수 인자로 받는다. 임의 org/project 파라미터를 service layer로 넘기지 않는다. 정상 API connection은 global 관리자 role이 아니다. PostgreSQL에는 모든 tenant table에 RLS와 `FORCE ROW LEVEL SECURITY`를 적용한다. transaction마다 검증된 tenant를 `SET LOCAL`로 설정하고 pool 반환 전 transaction을 종료한다. connection 재사용으로 이전 tenant context가 남는 시험을 포함한다. migration/backup role은 API에서 사용할 수 없고 해당 credential을 signer/worker에 전달하지 않는다.

RLS는 FK·application auth 대체물이 아니다. target/plan/evidence/cursor의 resource authorization은 별도 확인한다. SQLite는 DB 차원의 다중 tenant RLS가 없으므로 Lite 기본 한 tenant와 repository 검사로 제한한다. Team 다중 tenant 보장은 PostgreSQL profile의 출시 조건이다. Lite에 다중 tenant를 켜면서 Team 수준 격리로 표기하면 안 된다.

role_membership과 credential 변경은 authority/security revision 증가와 감사 이벤트를 만든다. 오래된 JWT에 role이 있더라도 현재 철회·project scope를 검증한다. read-model actions cache는 짧은 hint이며 승인/배포 transaction에서 사용하지 않는다. API scope와 workload binding principal이 다르면 명시적으로 허용된 on-behalf-of 근거 없이는 거절한다. worker 모델 출력은 그 근거가 될 수 없다.

## 8. evidence 저장·감사 원자성

evidence object는 임시 파일/객체에 write→fsync/완료 확인→hash 확인→content-addressed 이름으로 원자 확정 후 DB 참조를 commit한다. 경로는 store root+검증된 digest에서만 생성하고 사용자의 파일명/URL을 붙이지 않는다. symlink/reparse-point 탈출, 같은 hash의 다른 bytes, content-type 혼동을 거절한다. object store에서는 conditional put와 checksum 확인을 사용한다. hash 충돌 또는 immutable object 변경이 관측되면 incident와 해당 증적 사용 중단이다.

audit event append는 audit_heads를 잠그고 sequence+1, previous hash, event bytes, 새 head를 원자 commit한다. 순서상의 deadlock을 피하기 위해 업무 row와 audit head의 잠금 순서를 고정한다. audit 기록 실패 시 신규 권한 확대·승인은 실패로 끝낸다. 긴급 제한적 회수는 target 로컬 저널에 durable 기록 후 재접속 감사 동기화를 허용하되 감사 누락을 숨기지 않는다. 멀티 target transaction 성공으로 표현하지 않는다.

retention GC는 (1) 보존 기한, (2) legal/incident hold, (3) 활성 plan/authority/unknown operation 참조, (4) checkpoint 필요 여부를 확인한다. 삭제한 content는 availability=deleted와 원래 hash/사유를 남긴다. PBOM은 partial을 표시하며 존재하지 않는 증거를 complete라고 응답하지 않는다. 암호화 키 파기와 실제 content 삭제는 별도 작업으로 증거를 남긴다.

## 9. migration·업그레이드·rollback

1. release의 schema version, migration checksum, 최소/최대 app version을 검증한다. 예상치 못한 현재 version이면 시작을 거절하고 자동 downgrade하지 않는다.
2. 신규 dispatch를 pause하고 이미 발급된 grant/UNKNOWN 처리 현황을 보존한다. controller pause가 target의 만료와 watchdog을 멈추지 않게 한다.
3. SQLite online backup API 또는 PostgreSQL 일관 snapshot/복구 가능한 WAL 위치를 확보한다. 평문 secret을 포함한 backup을 공개 artifact에 넣지 않는다. backup manifest에 schema/checkpoint/최대 epoch/generation과 hash를 기록한다.
4. expand→backfill→validate→switch→contract 순서를 사용한다. 파괴적 column drop과 새 앱 전환을 한 단계로 하지 않는다. backfill은 bounded batch와 재시도 가능한 key를 사용하며 dual-write가 있으면 일치 검사를 한다.
5. nullable→NOT NULL, 새로운 FK/UK/CHECK, enum 변경은 기존 데이터 검증 뒤 활성화한다. 검증 실패 시 데이터 의미를 임의 수정하지 않는다.
6. rollback은 앱 binary와 호환 가능한 additive schema 상태로 되돌리는 것이 우선이다. 이미 외부 집행이 발생한 DB를 과거 backup으로 무조건 복원하면 안 된다. 복원 시 target/독립 checkpoint와 재조정하고 신규 grant를 quarantine한다.

migration transaction 밖에서 executor를 호출하지 않는다. 적용 중 crash 후 재시작은 schema_migrations checksum/state와 DB 원자성으로 완료/미완료를 결정한다. partially applied schema를 version number만 올려 정상으로 표시하지 않는다. PostgreSQL concurrent index처럼 transaction 밖 작업이 필요한 경우 migration 단계에 재진입 검사와 failure cleanup을 명시한다. 운영 롤백도 만료·철회·generation을 되돌리지 않는다.

## 10. 장애 행렬과 복구 결정

| 중단 시점 | durable 근거 | 재시작 동작 |
|---|---|---|
| request commit 전 | 아무 business row도 없음 | 같은 idempotency key로 새 transaction |
| request commit 후 응답 전 | idempotency+operation+outbox | 동일 응답 재전달 |
| artifact 확정 후 plan commit 전 | orphan bytes | 승인되지 않음; timeout GC |
| 예약 후 signer 응답 전 | intent/reservation | exact signer job 재시도; 신규 slot 중복 금지 |
| signer 성공 후 grant DB commit 전 | intent + signer의 exact result | 다시 검증 후 동일 grant 저장 또는 폐기; 전송 금지 |
| outbox commit 후 target 응답 전 | signed grant/outbox | 동일 grant 조회·replay; UNKNOWN이면 예약 유지 |
| target apply 후 controller down | target journal/watchdog/expiry | target 자체 confirm/rollback 규칙; 복구 뒤 receipt ingest |
| receipt 저장 후 UI 응답 전 | inbox/receipt/operation | 동일 operation 조회 |
| quota sweeper와 unknown reconcile 경합 | locked reservation+terminal receipt | 하나의 검증된 상태 전이만 slot 해제 |
| worker lease 만료와 complete 경합 | claim generation row | 현재 미만료 소유자만 성공 |
| old backup restore | 낮은 local epoch와 높은 target/checkpoint | quarantine, reconcile, 재등록; 자동 reopen 금지 |

## 11. 구현 검증의 완료 조건

정적 schema/문서 검사와 실제 DB/OS 검증을 구별한다. 출시 전 SQLite와 PostgreSQL 모두에서 다음 시험을 수행하고 commit/version/OS/filesystem을 기록한다.

- 같은 idempotency key 100회 병렬 요청→resource1개; 다른 body는409. 동일 policy revision 수정 race→한 개 성공, 나머지412.
- quota 상한 바로 아래에서 root/project를 공유한100개 병렬 발급→한도 이하만 성공. distinct destinations 중복·새주소·window 경계를 검사한다.
- 모든 T1~T8 commit 직전/직후 process kill과 재실행→참조 무결성, event/outbox 누락 없음, 중복 grant 비용 없음.
- 두 controller writer와 오래된 sender→target fencing으로 단일 writer 보장. DB lock만으로 통과한 시험은 불충분하다.
